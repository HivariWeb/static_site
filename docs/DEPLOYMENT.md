# Выпуск версии без онлайн-оплаты

Эта версия добавляет форму первичного обращения. ЮKassa, приём платежей и автоматическое создание договоров не подключены. Метрика подготовлена, но `metrikaId: 0` оставляет счётчик выключенным.

## Перед публикацией

1. Проверить актуальность услуг, цен, контактов и рабочих часов. Согласовать новую страницу `consent-request.html` и раздел 16 политики. Условия публичной оферты сохранены; пункты об объёме расширенного сопровождения, возвратах и неустойке требуют отдельной проверки владельцем и юристом.
2. Убедиться, что есть право на публикацию отзывов и сертификатов. Изображения сохранены из предыдущей версии, согласия клиентов технически не проверялись.
3. Сохранить свежую файловую копию хостинга и настройки виртуального хоста. Файловая копия не заменяет резервирование почты, баз данных и настроек панели.
4. Подтвердить PHP 8.1+ (проверено локально на PHP 8.3). На хостинге должны работать сессии, JSON, `random_bytes`, `hash_hmac`, `flock`, `rename`, `mail`. Сторонние PHP-библиотеки не требуются.

## Закрытая конфигурация и заявки

Корень сайта, видимый через FTP: `/www/dianaberezovskaya.online`.

Создать соседнюю приватную директорию `/www/diana-site-private`, которая **не является корнем другого публичного сайта**. Скопировать туда `config/hosting.example.php` под именем `config.php`. Файл конфигурации и данные заявок нельзя размещать внутри публичного каталога сайта или добавлять в Git.

Указанные пути — пути FTP. В PHP-конфигурации `storage_path` должен быть абсолютным путём файловой системы хостинга. В примере используется `__DIR__ . '/storage'`, поэтому вручную угадывать `/var/www/...` не нужно. Приложение по умолчанию ищет приватный конфиг в соседней директории `diana-site-private`. При другой структуре задать серверную переменную `DIANA_CONFIG_PATH` с абсолютным путём к конфигу.

Настроить:

- `secret`: случайный секрет, например результат `bin2hex(random_bytes(32))`; хранить только в приватном конфиге. Не менять во время обработки открытых форм: он участвует в защите идентификаторов и ограничении частоты.
- `notification_email`: `dianagulchenko@yandex.ru` — адрес согласован владельцем.
- `from_email`: адрес собственного домена `dianaberezovskaya.online`. Предложенный `no-reply@...` нужно проверить с почтовыми настройками REG.RU; наличие и доставляемость такого отправителя локальные тесты не подтверждают.
- `mail_enabled`: оставить `false` до согласованной проверки почты, затем включить `true`.
- `allowed_origins`: `https://www.dianaberezovskaya.online`.

Хранилище создаётся с правами 0700, файлы — 0600 на системах с POSIX-правами. Приложение отклоняет конфигурацию, если хранилище разрешается внутрь публичной папки. На Windows применяются также права каталога пользователя.

Форма сохраняет имя, контакт, услугу, подтверждение согласия и контрольную сумму документа. Медицинская анкета и произвольный комментарий отсутствуют. Метки источника сохраняются только при отдельном разрешении аналитики. Заявка сначала записывается на диск, затем выполняется попытка уведомления. Сбой почты не отменяет сохранение и не превращает повторную отправку в новую заявку.

`notification.status = sent` означает передачу письма почтовому транспорту, а не доказанную доставку в ящик. После включения почты нужно проверить получение сообщения и папку спама. Для реальной контрольной заявки использовать данные владельца и согласованный тест, а затем удалить тестовую запись.

## Обслуживание и хранение

Настроить CRON в панели REG.RU каждые пять минут:

```text
/абсолютный/путь/к/php /абсолютный/путь/к/сайту/tools/maintenance.php
```

Точные пути PHP и сайта взять из панели хостинга. При нестандартном размещении конфига передать `DIANA_CONFIG_PATH` через окружение задания.

Скрипт удаляет заявки после срока хранения (не более 90 дней), старые ограничения частоты и файлы сессий; повторяет отправку до 20 ожидающих уведомлений за запуск. Он выполняется только из CLI и не выдаёт данные заявок по HTTP. Проверить успешный ручной запуск, затем настроить уведомления о сбоях задания средствами хостинга. Доступ к CRON через один FTP не подтверждён.

Сырые записи в `storage/leads/` доступны владельцу через защищённый файловый доступ. При необходимости передачи запроса в договорную работу хранение договорных материалов организуется отдельно. Не переносить заявки в репозиторий, аналитику или публичные логи. Резервные копии с реальными заявками тоже должны иметь ограниченный доступ и установленный срок хранения.

## Файлы выпуска

Выполнить:

```text
python tools/prepare-release.py
```

Команда обновляет версии CSS/JS, CSP-хеш JSON-LD и `config/deployment-manifest.json`. Публиковать только файлы из этого списка. Архивы, Git, аудит, тесты, приватный конфиг, DOCX и старые snippets в публикацию не включаются. Перед загрузкой нужно сверить SHA-256 файлов с манифестом.

Сначала загрузить зависимости: шрифты, ресурсы, общие шаблоны и PHP-модули; HTML обновлять после них. Из-за обновления старых файлов возможна краткая несовместимость при прямой загрузке. Предпочтителен выпуск через подготовленную директорию и атомарное переключение средствами хостинга. Возможность такого переключения в текущем FTP-аккаунте не проверена.

При выпуске очистить из старой публичной папки только заранее перечисленные и сохранённые в резервной копии служебные файлы: `*_snippet.*`, три исходных DOCX и `.vscode/settings.json`. Не удалять незнакомые файлы рекурсивно. Старый `send-email.php` заменяется ответом 410 и ссылкой на новую запись.

## Проверки на хостинге

- HTTPS открывает главную, документы, шрифты и форму без 500, ошибок JavaScript и CSP.
- HTTP, адрес без `www` и `/index.html` перенаправляются на основной HTTPS-адрес. Рекламные query-параметры сохраняются. Проверить отсутствие цикла с учётом прокси REG.RU: в `.htaccess` используются `HTTPS` и `X-Forwarded-Proto`. Доверять заголовку прокси можно только если хостинг перезаписывает его, а прямой доступ к backend закрыт.
- Директории `config`, `includes`, `tools`, Git, аудит и служебные файлы не доступны по HTTP. Nginx может обслуживать статические файлы самостоятельно: нельзя считать Apache `.htaccess` единственным подтверждением защиты, нужно проверить реальные URL и убрать лишние файлы из web-root.
- `request.php` и API отдают `Cache-Control: no-store`; технический cookie имеет HttpOnly, SameSite=Lax и Secure на HTTPS.
- Контрольная заявка сохраняется в приватном каталоге; версия согласия соответствует документу. Повтор не создаёт вторую запись. Ошибка в почте оставляет уведомление в очереди.
- Получено письмо на рабочий адрес, подтверждён отправитель и проверены SPF/DKIM/DMARC для фактического почтового маршрута.
- CRON действительно выполняется; права, свободное место и очередь уведомлений проверены.
- Ограничение частоты использует `REMOTE_ADDR`, а не произвольный клиентский `X-Forwarded-For`. Убедиться, что REG.RU передаёт в PHP настоящий адрес посетителя; если там виден общий адрес прокси, сначала исправить настройку доверенного прокси у провайдера.
- Повторный визит получает актуальные версии CSS/JS. `robots.txt`, `sitemap.xml` и страница 404 открываются корректно.

До активации Метрики отдельно создать счётчик и цели согласно `docs/ANALYTICS.md`. Модерация рекламы, бюджет, регистрационные обязанности оператора данных и юридическая проверка не выполняются автоматически этим выпуском.

## Откат

Остановить приём заявок, сохранить приватные данные, восстановить публичные файлы из последней проверенной копии, включая прежний `.htaccess` или его отсутствие. Приватный каталог при откате не удалять. Убедиться, что форма не сообщает об успешном сохранении, когда новый API отключён. Не смешивать старый HTML и новые ресурсы без проверки.
